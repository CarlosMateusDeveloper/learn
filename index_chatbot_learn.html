Chatbot de agendamento:
nome → especialidade → link

Este guia implementa o fluxo de agendamento do chatbot em cima da estrutura que já existe no módulo (controllers, services, models). O fluxo é curto de propósito: o paciente diz o nome, escolhe a especialidade e recebe o link onde marca o horário. Siga as seções na ordem — cada uma é testável antes da próxima.

1

O fluxo em uma tela

Antes do código, veja a conversa que vamos construir, do ponto de vista do paciente:

paciente
Oi
bot
Olá! 👋 Bem-vindo(a) ao agendamento da clínica. Para começar, me diga o seu nome:
paciente
Maria Souza
bot
Prazer, Maria Souza! 😊 Qual especialidade você procura? 1 - Clínico geral 2 - Cardiologia 3 - Dermatologia 4 - Pediatria 5 - Ortopedia Responda com o número da opção.
paciente
2
bot
Perfeito, Maria Souza! ✅ Escolha o melhor horário de Cardiologia aqui: https://clinica.com/agendar/cardiologia Depois de agendar, você recebe a confirmação por aqui.

Três etapas, três mensagens do bot. Tudo que vem a seguir existe para produzir exatamente essa conversa — nem mais, nem menos.

2

Onde o código mora

Um arquivo novo, no lugar que a estrutura do módulo reserva para regra de negócio:

chatbot/ ├── controllers/ # não muda — continua sem regra de negócio ├── services/ │ ├── whatsapp_service.py # já existe (envio — passo 4 do guia geral) │ ├── mensagem_service.py # já existe (é quem vai CHAMAR o fluxo) │ └── conversa_service.py # ★ o arquivo deste guia ├── models/ # não muda — nada de tabela ou coluna nova └── views/ # não muda
Regra do projeto que continua valendo: controller não decide nada; decisão mora em service. O conversa_service é puro "o que responder" — ele não sabe enviar mensagem nem salvar no banco. Quem orquestra é o mensagem_service (seção 7).
3

A decisão: estado em memória

O bot precisa lembrar em que etapa da conversa cada telefone está: esperando o nome? esperando a especialidade? já concluiu? Isso é o "estado da conversa" — e a pergunta é onde guardá-lo.

O lugar óbvio seria uma coluna nova na tabela paciente. Mas o guia geral do módulo é claro: o schema do banco não é do chatbot — criar coluna é uma conversa com quem mantém o banco, não uma decisão unilateral daqui. Então a escolha deste guia é um dicionário em memória:

# telefone -> {"etapa": ..., "nome": ...}
_conversas: dict[str, dict] = {}
O custo assumido (e por que ele é aceitável): se o servidor reiniciar no meio de uma conversa, o paciente volta para o início. Para um fluxo de 3 passos que dura menos de um minuto, esse custo é pequeno. Se um dia incomodar, o upgrade é a coluna etapa_conversa — negociada com o time do banco, não improvisada aqui.
Não faça: criar tabela conversa por conta própria "só para o chatbot", nem gravar a etapa em arquivo local. As duas opções criam uma segunda fonte de verdade escondida — exatamente o tipo de decisão que o guia geral pede para alinhar antes.
4

Configuração do fluxo

Tudo que muda de clínica para clínica fica no topo do arquivo — especialidades e textos. Para acrescentar uma especialidade amanhã, você mexe só aqui:

ESPECIALIDADES = {
    "1": ("Clínico geral", "clinico-geral"),
    "2": ("Cardiologia", "cardiologia"),
    "3": ("Dermatologia", "dermatologia"),
    "4": ("Pediatria", "pediatria"),
    "5": ("Ortopedia", "ortopedia"),
}
# cada opção = (rótulo mostrado no chat, slug usado no link)

O link de agendamento é montado com uma base vinda do .env + o slug da especialidade — funciona tanto se a página de horários for do próprio sistema quanto se for um Calendly por especialidade:

# .env
AGENDAMENTO_URL_BASE=https://clinica.com/agendar

# config.py — mesmo padrão das outras variáveis do módulo
AGENDAMENTO_URL_BASE = os.getenv("AGENDAMENTO_URL_BASE")
Regra do projeto: nada de URL ou credencial hardcoded — sempre via .env, que já está no .gitignore.
5

A máquina de conversa

O coração do arquivo é uma função só: recebe o telefone e o texto, olha a etapa atual e devolve o texto da resposta. Ela não envia nada — só decide:

def responder(db, telefone: str, texto: str) -> str:
    texto = (texto or "").strip()
    estado = _conversas.get(telefone)

    # ---- primeira mensagem deste telefone (ou estado perdido) ----
    if estado is None:
        nome = _nome_do_cadastro(db, telefone)   # seção 6
        if nome:  # já é paciente: pula a pergunta do nome
            _conversas[telefone] = {"etapa": "aguardando_especialidade", "nome": nome}
            return _msg_menu(nome)
        _conversas[telefone] = {"etapa": "aguardando_nome", "nome": None}
        return MSG_BOAS_VINDAS

    # ---- etapa: esperando o nome ----
    if estado["etapa"] == "aguardando_nome":
        nome = texto.title()
        if len(nome) < 2 or nome.isdigit():
            return MSG_NOME_INVALIDO
        estado["nome"] = nome
        estado["etapa"] = "aguardando_especialidade"
        return _msg_menu(nome)

    # ---- etapa: esperando a especialidade ----
    if estado["etapa"] == "aguardando_especialidade":
        escolha = ESPECIALIDADES.get(texto)
        if escolha is None:
            return _msg_opcao_invalida()
        rotulo, slug = escolha
        estado["etapa"] = "concluido"
        return _msg_link(estado["nome"], rotulo, slug)

    # ---- concluído: qualquer mensagem reabre o menu ----
    estado["etapa"] = "aguardando_especialidade"
    return MSG_RECOMECO

Repare no formato: cada etapa é um bloco, cada bloco valida a entrada e ou avança a etapa ou repete a pergunta. Entrada inválida nunca avança — nome numérico volta a pedir o nome, opção fora do menu repete as opções.

As mensagens são funções pequenas que montam texto (os templates completos estão no arquivo conversa_service.py que acompanha este guia):

def _msg_link(nome: str, rotulo: str, slug: str) -> str:
    link = f"{AGENDAMENTO_URL_BASE}/{slug}"
    return (
        f"Perfeito, {nome}! ✅\n"
        f"Escolha o melhor horário de {rotulo} aqui:\n\n"
        f"{link}\n\n"
        "Depois de agendar, você recebe a confirmação por aqui."
    )
6

Paciente já cadastrado

Se o telefone já corresponde a um paciente na tabela, perguntar o nome de novo seria robótico. A função abaixo consulta o cadastro e, se achar, o bot cumprimenta pelo primeiro nome e vai direto ao menu:

def _nome_do_cadastro(db, telefone: str) -> str | None:
    # no banco o telefone está separado em ddd + numero,
    # mas ele chega como string única (ex.: "5584999999999")
    ddd, numero = telefone[-11:-9], telefone[-9:]
    contato = (
        db.query(Contato)
        .filter(Contato.ddd == ddd, Contato.numero == numero)
        .first()
    )
    if contato and contato.nome and contato.nome.strip():
        return contato.nome.split()[0].title()  # primeiro nome basta no chat
    return None
Ponto de atenção real: o fatiamento [-11:-9] assume 11 dígitos de DDD+número no fim da string (funciona com ou sem o 55 do país na frente). Antes de confiar, imprima o telefone exato que o SEU provedor entrega no webhook e ajuste — número fixo de 10 dígitos, por exemplo, quebraria essa conta. É o mesmo tipo de separação já prevista no passo 2 do guia geral.
7

Ligando no process_incoming_message

O mensagem_service.process_incoming_message (passo 5 do guia geral) continua dono da orquestração. O fluxo dele passa a ser:

from chatbot.services import conversa_service, whatsapp_service

async def process_incoming_message(db, telefone: str, texto: str):
    # 1. salvar a mensagem recebida (direcao="entrada"),
    #    vinculando ao paciente se o telefone for conhecido
    salvar_mensagem(db, telefone, texto, direcao="entrada")

    # 2. perguntar ao fluxo o que responder
    resposta = conversa_service.responder(db, telefone, texto)

    # 3. enviar — e só registrar a saída se o envio deu certo
    enviado = await whatsapp_service.send_message(telefone, resposta)
    if enviado:
        salvar_mensagem(db, telefone, resposta, direcao="saida")
Divisão de responsabilidades: conversa_service decide o texto; whatsapp_service envia; mensagem_service salva e coordena. Nenhum dos três invade o trabalho do outro — se amanhã o fluxo mudar, só o primeiro arquivo é tocado.
Substitui a boas-vindas antiga: a lógica de "se for a primeira mensagem, mandar boas-vindas" do passo 5 do guia geral agora vive dentro do responder — não deixe as duas coexistindo, ou o paciente novo recebe duas saudações.
8

Como testar

Como sempre no projeto: teste manual pelo /docs antes de qualquer teste automatizado. Simule a sequência inteira mandando POSTs no /webhook com o payload do seu provedor, variando só o texto:

# sequência de textos para um telefone que NÃO existe na tabela paciente
1º POST  texto="oi"            # espera: boas-vindas pedindo o nome
2º POST  texto="123"           # espera: pedir o nome de novo (inválido)
3º POST  texto="Maria Souza"   # espera: menu de especialidades
4º POST  texto="9"             # espera: opção inválida, repete opções
5º POST  texto="2"             # espera: link .../agendar/cardiologia
6º POST  texto="obrigada"      # espera: reabrir o menu (recomeço)

Depois, repita o 1º POST com um telefone que existe na tabela paciente — o bot deve pular a pergunta do nome e ir direto ao menu, cumprimentando pelo primeiro nome.
